## Summary

No blocker found. The FFI signatures are correct for x64 Windows. BOOL is `int`, HWND and HMONITOR are `intptr_t`, and `long` is 32-bit in RECT, POINT and the HRESULT return. MONITORINFO is 40 bytes. The GetClassNameW buffer is 512 bytes for a max of 256 characters. The DwmGetWindowAttribute out parameter is an int32 array. GetWindowLongPtrW is masked to 32 bits.

These checks passed:
- `node --test` passes, 502 of 502.
- `probeForeground([0, 1])` returns a real sample here (class `CASCADIA_HOSTING_WINDOW_CLASS`, integer hwnd, `gone: [0, 1]`).
- On this machine (2 displays: 100% primary and 125% secondary), `screen.dipToScreenRect(null, bounds)` returned the exact physical rect for both. The secondary came back as `-1920,0,1920x1080`. So the null-window call does not use the primary's scale, and there is no mixed-DPI bug at these scales.
- `require('./fullscreen')` does not load koffi. The load only happens inside `loadNativeApi`, behind the win32 guard and a try.
- `hook.js`, `permission-hook.js`, `window.js`, `state.js`, `install.js` and `preload.js` do not cite the package.
- Nothing from the sample is logged. The only `console.error` prints `error.message` once, when the load fails.
- Security boundary: covering only ever hides the island. `island:decide` and `acceptDecision` are untouched, `windowVisible` is false while hidden, and the 0.5 s staleness window in either direction fails safe. When the island is uncovered, `showInactive` fires `'show'`, which calls `refresh('rearm')`.
- `start()` ordering is fine. `probeFullscreen()` runs before `syncIslands()`, so `applyVisibility` has nothing to iterate. `createIsland` reads the map for `show:`, so a monitor that is already covered is created hidden.
- The in-place map replace and the compare are correct. The `Map` const is shared by `island:decide`, `createIsland` and the shortcut.

The findings below are about robustness and test strength.

## Warnings

### WR-01: Monitor-to-display match uses exact equality, so fractional DPI scales can disable the sensor without any signal

**File:** `state.js:212-214` (consumer), `main.js:254-256` (producer)
**Issue:** `nextFullscreen` finds the display with `sameRect(candidate.rect, foreground.monitorRect)`, an exact four-side comparison. Only the client rect against the display gets the 1 px tolerance. `candidate.rect` is `screen.dipToScreenRect(null, display.bounds)`, a round trip from physical to DIP (integer, rounded or floored) and back to physical. That round trip is exact at 100% and 125% for 1920x1080 and 2560x1080, which is all that was measured here. At scales that don't divide the panel evenly, the DIP size is rounded and scaling it back lands off by up to a pixel or more from `rcMonitor`.
- Example: a 2560x1440 panel at 175% gives a DIP size of about 1462.9 x 822.9.
- If Chromium rounds it down to 1462 x 822, the physical rect is 2558.5 x 1438.5, which is not 2560 x 1440.
- Common laptop panels (1920x1080 at 125% is fine, but 150%, 175% and 225% on 4K) are exposed.

I could not reproduce this because this machine only has 100% and 125% displays. It is a risk that follows from the arithmetic, not a measured failure. When it happens, `display` is `undefined`, `nextFullscreen` returns `result` unchanged, and the island silently stays on top of the fullscreen app. No log and no test covers it.

**Fix:** match with the same tolerance, or by best overlap. In `state.js`:
```js
const near = (a, b) => ['left', 'top', 'right', 'bottom'].every((side) => (
  Number.isFinite(a?.[side]) && Number.isFinite(b?.[side]) && Math.abs(a[side] - b[side]) <= 2
));
const display = knownDisplays.find((candidate) => near(candidate?.rect, foreground.monitorRect));
```
Add an `island.test.js` case with a monitor rect 1 px off the display rect. Better still, measure on a 150% or 175% display before merge and add that to the manual script.

### WR-02: The new gate.test.js locks do not pin the part of the wiring that actually updates the map

**File:** `gate.test.js:1243-1245` (against `main.js:253-268`)
**Issue:** The text lock for `probeFullscreen` only looks for the substrings `process.pid`, `screen.dipToScreenRect(null, display.bounds)`, `nextFullscreen(` and `applyVisibility(`. Each of these mutations still passes all 502 tests:
- Deleting `fullscreenByDisplay.clear()` or the `for (...) fullscreenByDisplay.set(...)` loop. The map then never updates, so a monitor stays hidden forever or the sensor does nothing, and the island stays hidden after the app exits.
- Changing `probeForeground([...fullscreenByDisplay.values()])` to `probeForeground([])`. The remembered HWNDs are then never checked for `gone`, so closed, minimized and cloaked windows never release the monitor. The plan's own `key_links` pattern for this call is not asserted anywhere.
- Passing `previous: new Map()` to `nextFullscreen`. The remembered-HWND behavior (D-18, focusing the other monitor keeps A hidden) is lost.
- Wrapping `fullscreenByDisplay` in a new object each tick instead of replacing in place, which breaks the `island:decide` read.
- A hook that does `require('./fullscreen')` passes every lock. This one is harmless because the load is lazy, but T-03w-01 says to forbid it.

Separately, `'process.pid'` can be satisfied by a comment. `probeFullscreen` is the logic most likely to regress, and it can only be tested through text.

**Fix:** extend the needles with `probeForeground([...fullscreenByDisplay.values()])`, `previous: fullscreenByDisplay`, `fullscreenByDisplay.clear()` and `fullscreenByDisplay.set(`. Or extract the "replace the map in place and report whether it changed" step into a pure helper in `state.js` and unit-test it. Optionally assert that no hook file contains `./fullscreen`.

## Info

### IN-01: A remembered HWND is only released when it disappears or something else takes focus on its monitor

**File:** `fullscreen.js:67-70`, `fullscreen.js:115-127`
**Issue:** `gone` is computed only from `IsWindow`, `IsWindowVisible`, `IsIconic` and cloaked. If a remembered window is still visible but is no longer fullscreen, and focus is on another monitor, the monitor stays "covered" and its island stays hidden. An example is a player that leaves fullscreen on its own. The behavior is fail-safe (hidden means the gate refuses), but it breaks the README promise that the island comes back "quando ele sai". The `ponytail:` note in `state.js` only covers the opposite case.
**Fix:** also drop a remembered HWND whose current client rect no longer covers its monitor. This would be another `GetClientRect` and `ClientToScreen` per remembered HWND inside `isGone`. Or accept it and add a line to the README or a ponytail comment.

### IN-02: Transient full-monitor system windows and flyouts will flicker the island (not verified)

**File:** `state.js:213-228` (rule), `fullscreen.js:72-112` (sensor)
**Issue:** Only four shell classes are excluded. Any foreground window whose client area equals the monitor counts, such as the Win11 Alt+Tab and Win+Tab overlay, the screenshot overlay, or a Start-menu core window when it covers the monitor. Those would hide the island and then show it again, and the `'show'` event rearms the buttons. The reverse also applies. Opening Start or a flyout over a real fullscreen video moves the foreground to a small window on that monitor, which releases the monitor and makes the island appear over the video until the video is refocused. This follows from D-18 as designed and I could not test it, so it is reported as a possible nuisance, not a defect. The manual script does not cover Alt+Tab or Start.
**Fix:** add Alt+Tab and Start over a fullscreen video to the PR manual test script. If it is annoying, add the offending classes to `SHELL_WINDOW_CLASSES` or ignore windows owned by `explorer.exe`.

### IN-03: Maximized windows with an auto-hide taskbar are not covered by the manual script, and the tolerance is 1 px

**File:** `state.js:181` (`FULLSCREEN_TOLERANCE_PX = 1`), the manual script in `261122-03w-SUMMARY.md`
**Issue:** The "maximized terminal" check only covers a visible taskbar, where the client area is the work area and is smaller than the monitor, so it is safe. With an auto-hide taskbar, a maximized custom-frame app (the client area includes the title bar) fills the monitor except for the sliver the taskbar keeps. Chromium-based apps use a 2 px sliver. If any app leaves only 1 px, it would be treated as fullscreen and its island would be hidden. I could not test this because I did not change the taskbar setting.
**Fix:** run the maximized-terminal check once with the taskbar set to auto-hide. If an app leaves a gap of at most 1 px, handle it (for example, also require no `WS_MAXIMIZE` style).

### IN-04: `probeFullscreen` has no catch of its own, and the lockfile holds more than the two packages the summary mentions

**File:** `main.js:253-268`, `main.js:808-812`, `pnpm-lock.yaml`
**Issue:**
- (a) `probeForeground` and `nextFullscreen` never throw, but `applyVisibility()` and `screen.*` can. For example, `island.isVisible()` on a destroyed window throws. An exception in the timer shows an Electron error dialog in the main process. The first call in `start()` would abort `start()` before `syncIslands()` and the poll timer. The project convention is to log in pt-BR and keep running. This is unlikely today.
- (b) The lockfile diff adds `koffi@3.3.8` plus 20 `@koromix/koffi-<platform>` entries, with integrity hashes and `os`/`cpu` fields. The SUMMARY says `Packages: +2`, which is what installs on Windows x64, and the lockfile is as pnpm normally records optional dependencies. Only `win32-x64` was installed here. It is not wrong, but D-20's author confirmation should cover the hashes for all the platform packages, not just the one that ran.
**Fix:** (a) wrap the body in `try { ... } catch (error) { console.error('Falha na sondagem de tela cheia:', error.message); }`. (b) Note it in the PR text.
